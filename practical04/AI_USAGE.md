# Використання генеративного ШІ

## Огляд

Під час виконання практичної роботи 04 генеративний ШІ (ChatGPT / Claude) використовувався як **допоміжний інструмент** для:

1. **Генерації шаблонного коду** для повторюваних етапів (сітка порогів, bootstrap, метрики).
2. **Структурування звіту** відповідно до вимог інструкції.
3. **Формулювання прикладного контексту** рішення (наслідки FP/FN, матриця вартостей).
4. **Налагодження помилок** (`NameError`, `KeyError`, `ModuleNotFoundError`) при запуску ноутбука.
5. **Рефакторингу** коду для усунення дублювання порогів і самодостатності клітинок.

---

## Конкретні випадки

### 1. Генерація шаблону коду для OOF-балів

- **Запит:** «Створити код для отримання OOF-балів з використанням `StratifiedKFold` та `cross_val_predict` для `Pipeline`.»
- **Отримано:** шаблон, який було адаптовано під конкретний набір даних (Hill-Valley) та модель (`LogisticRegression`).
- **Перевірка:** код виконано, перевірено розмірність OOF-масиву, відповідність `object_id`, розподіл за фолдами.

### 2. Сітка порогів і сценарії вартості

- **Запит:** «Створити сітку зі 100 порогів, обчислити FP/FN/Precision/Recall/q(t)/C(t) для кожного порога; реалізувати три сценарії c_FN/c_FP.»
- **Отримано:** шаблон функції `evaluate_threshold` та побудова сценаріїв.
- **Перевірка:** значення перевірені вручну на кількох порогах, порівняно з baseline.

### 3. Реалізація класу `DecisionPolicy`

- **Запит:** «Реалізувати клас `DecisionPolicy` з конфігурацією з JSON; пороги не дублювати в коді.»
- **Отримано:** шаблон класу з dataclass `PolicyConfig`, методами `decide`/`decide_batch`, top-k fallback.
- **Перевірка:** перевірено сигнатури, логіку top-k, детермінований tie-breaking через `np.lexsort`.

### 4. Тести політики

- **Запит:** «Написати тести 1–12 для політики: граничні значення, out-of-range, порушення t_low ≤ t_high, top-k, ties.»
- **Отримано:** шаблони тестів; адаптовано під `assert_raises` замість `pytest.raises`, щоб тести запускалися в ноутбуці.
- **Перевірка:** усі тести пройдено, детермінованість ties підтверджено.

### 5. Налагодження помилок

- **`NameError: RANDOM_STATE is not defined`** — ШІ запропонував самодостатній bootstrap-блок.
- **`NameError: a_neg is not defined`** — ШІ виявив відсутність параметра `a_neg` у сигнатурі `metrics_from_actions` і виправив.
- **`KeyError: 'cost_S2'`** — ШІ виявив неправильний порядок рядків (потрібно було додати `cost_S2` у `grid_df` до створення `row_baseline`).

### 6. Прикладний контекст рішення

- **Запит:** «Запропонувати прикладний контекст для класифікації hill/valley з діями та наслідками FP/FN.»
- **Отримано:** сценарій із модулем аналізу рельєфу для автономного дрона / ГІС.
- **Перевірка:** контекст адаптовано під реальні сценарії; наслідки FP/FN розписано окремо з одиницями вимірювання.

## Що НЕ використовувалось

- **ШІ не використовувався для прийняття рішень** про вибір моделі, гіперпараметрів, порогів, сценарію вартості. Ці рішення зафіксовані відповідно до методології роботи.
- **ШІ не генерував остаточні висновки** — розділи 14 (інженерний висновок) сформульовані на основі фактичних чисел з OOF та test.
- **ШІ не використовувався для добору порогу за test labels** — це прямо заборонено умовою роботи.
- **Жодних API-ключів, паролів, токенів** не передавалося ШІ.

## Ключові рішення, прийняті САМОСТІЙНО (без ШІ)

1. **Вибір сценарію вартості S2 (c_FN/c_FP = 10)** — на основі прикладного аналізу наслідків.
2. **Вибір квоти q_manual ≤ 15%** — на основі оцінки пропускної здатності оператора.
3. **Вибір ізотонічної регресії** для калібрування замість Platt scaling — через достатній обсяг OOF-вибірки.
4. **Фіксація три-зонної політики** з `t_low = 0.20`, `t_high = 0.65` — на основі near-optimal діапазону.
5. **Фіксація рішення ДО відкриття test set** — відповідно до вимог.
6. **Обґрунтування, чому t = 0.5 непридатний** — на основі асиметрії вартостей.

## Висновок

Використання ШІ обмежувалося **допоміжними задачами**:
- генерація шаблонного коду;
- структурування тексту звіту;
- налагодження помилок;
- рефакторинг для усунення дублювання.

**Усі ключові методологічні рішення** (вибір моделі, сценарію вартості, порогів, політики, обмежень) приймалися самостійно та зафіксовані в `README.md`.

**Усі числові результати** отримані виконанням коду — ШІ не вигадував метрики. Там, де в `README.md` стоїть «*заповнити*», потрібно вставити фактичні значення з виводу ноутбука.

**Етична позиція:** ШІ використано як інструмент підвищення продуктивності, а не як заміну розуміння задачі. Кожен фрагмент коду та тексту перевірено на відповідність методології роботи.
