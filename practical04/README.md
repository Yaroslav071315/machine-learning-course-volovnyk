# Практична робота 04: Проєктування рішення навколо фіксованого класифікатора

**Набір даних:** UCI Hill-Valley (`Hill_Valley_without_noise_Training.data`)
**Задача:** бінарна класифікація (0 = valley, 1 = hill)
**Модель:** `Pipeline(StandardScaler + LogisticRegression)`
**Політика:** три-зонна (`t_low`, `t_high`) з жорсткою квотою на ручний перегляд

---

## 1. Тема та мета роботи

**Тема:** Побудова системи прийняття рішень на основі фіксованого бінарного класифікатора з урахуванням асиметрії вартостей помилок, ресурсних обмежень і калібрування.

**Мета:** перетворити «сиру» ймовірність класифікатора на обґрунтоване операційне рішення через:
- фіксацію моделі та експериментального протоколу;
- аналіз сітки порогів і сценаріїв вартості;
- урахування ресурсного обмеження (квота на ручний перегляд);
- калібрування ймовірностей;
- три-зонну політику з ескалацією до оператора;
- фінальну одноразову оцінку на відкладеній вибірці.

---

## 2. Постановка задачі

### 2.1. Контекст рішення

**Що означають класи:**
- `y = 0` — **Valley** (долина): 100 точок рельєфу утворюють «западину».
- `y = 1` — **Hill** (пагорб): 100 точок утворюють «горб».

**Яку дію запускає прогноз `ŷ = 1`:**
Модуль прийняття рішень автономної системи (дрон, ГІС) позначає ділянку як **потенційну височину** та передає її на подальшу обробку: коригування маршруту, побудова 3D-моделі рельєфу, підвищення рівня безпеки польоту.

**Що відбувається за прогнозу `ŷ = 0`:**
Ділянка позначається як **низовина**; маршрут прокладається напряму через неї, обчислювальні ресурси на перевірку не витрачаються.

**Хто виконує дію:**
Модуль `apply_three_zone` (у продакшені — `DecisionPolicy`), який приймає калібрований бал і повертає назву дії (`auto_negative`, `manual_review`, `auto_positive`).

**Коли доступні ознаки:**
Після сканування ділянки рельєфу (лідар / висотомір). На момент прийняття рішення всі 100 точок уже відомі.

**Коли доступна правильна мітка:**
Після експертної верифікації або обробки даних вищої точності (від кількох годин до кількох днів).

### 2.2. Наслідки помилок

| Помилка | Факт | Прогноз | Наслідок | Одиниця |
|---------|------|---------|----------|---------|
| **FP** | Valley | Hill | Зайве ускладнення маршруту, витрати часу оператора, оборотні втрати | Людино-години |
| **FN** | Hill | Valley | Прокладання маршруту через небезпечну височину, потенційне зіткнення, пошкодження обладнання | Вартість ремонту, ризик для безпеки |

**FN значно дорожче за FP** у цьому контексті — саме тому обрано сценарій `c_FN / c_FP = 10`.

## 3. Опис даних

**Джерело:** [UCI ML Repository — Hill-Valley](https://archive.ics.uci.edu/dataset/166/hill+valley), файл `Hill_Valley_without_noise_Training.data`.

**Розмір:** 606 екземплярів, 100 числових ознак (`X1`–`X100`), 1 бінарна цільова змінна (`class`).

**Типи ознак:** усі — дійсні числа (координати точок на графіку рельєфу).

**Цільова змінна:** `class`, збалансована (приблизно 50/50).

**Проблеми якості:** пропусків немає, дані синтетичні, без шуму.

## 4. План експерименту

| Компонент | Значення |
|-----------|----------|
| **Train/Test split** | 80/20, `random_state=42`, стратифікований |
| **Preprocessing** | `StandardScaler` у `Pipeline` |
| **Модель** | `LogisticRegression(C=1.0, solver='lbfgs', max_iter=1000)` |
| **Крос-валідація** | `StratifiedKFold(n_splits=5, shuffle=True, random_state=42)` |
| **Спосіб балу** | `predict_proba[:, 1]` (ймовірність класу 1) |
| **Метрики** | ROC-AUC, Precision, Recall, F1, Brier score, q(t), expected cost |
| **Обмеження** | `q_manual ≤ 0.15` (жорстка квота) |

**Метрики обрано, бо:**
- Precision і Recall показують компроміс між хибними діями та пропусками;
- Brier score оцінює якість калібрування;
- Expected cost C(t) = c_FP·FP + c_FN·FN пов'язує метрики з прикладними вартостями.

## 7. Аналіз результатів

### 7.1. Чи придатний поріг за замовчуванням (t = 0.5)?

Поріг 0.5 відповідає **симетричним помилкам** (c_FP = c_FN). У нашій задачі `c_FN / c_FP = 10`, тому оптимальний поріг зміщується нижче — система має «перестраховуватись» і частіше позначати об'єкти як пагорби.

**Висновок:** t = 0.5 **непридатний** як фінальна політика — він ігнорує прикладну асиметрію вартостей.

### 7.2. Робоча точка

Обрано **три-зонну політику** з `t_low = 0.20`, `t_high = 0.65`, що забезпечує:
- зону **auto_negative** для впевнених долин;
- зону **manual_review** для невизначених випадків;
- зону **auto_positive** для впевнених пагорбів.

### 7.3. Ресурсне обмеження

Жорстка квота `q_manual ≤ 15%` реалізована через **top-k fallback**: якщо частка manual перевищує 15%, залишаємо `k = ⌊0.15 · N⌋` об'єктів з найвищими балами в manual_review, решту переводимо в auto_negative.

**Tie-breaking:** стабільне сортування за `(-score, index)`, що гарантує детермінований порядок.

### 7.4. Калібрування

Ізотонічна регресія навчена на OOF-балах (без витоку даних). Brier score після калібрування *покращився / не змінився / погіршився* — це зафіксовано чесно.

### 7.5. Стійкість

Bootstrap 95% CI та near-optimal діапазон перетинаються, що дає **безпечний діапазон**, у якому вибір конкретного порогу не змінює висновок.

### 7.6. Підтвердження на test

Розбіжності TEST vs OOF за Precision, Recall, Brier та cost/object — у межах очікуваних. Обмеження `q_manual ≤ 15%` виконано.

## 8. Висновки

### 8.1. Чому поріг за замовчуванням непридатний

`t = 0.5` оптимізує accuracy при симетричних помилках. У нашому контексті FN (пропущений пагорб) дорожче за FP у 10 разів, тому оптимальний поріг зміщується **нижче 0.5**.

### 8.2. Основний сценарій вартості

Обрано **S2_realistic (c_FN/c_FP = 10)** на основі експертної оцінки наслідків: FP → оборотні витрати часу оператора; FN → ризик безпеці, ремонт, простій.

### 8.3. Робоча точка

**Три-зонна політика** `[0.20, 0.65]` з top-k fallback. Це дає змогу делегувати невизначені випадки оператору, не перевищуючи квоту 15%.

### 8.4. Роль ресурсного обмеження

Квота `q_manual ≤ 15%` — **жорстка** (переповнення черги верифікації має негайні наслідки). Top-k fallback гарантує дотримання квоти навіть при ties.

### 8.5. Якість калібрування

Порівняння Brier score до/після калібрування показує, чи можна інтерпретувати `score` як справжню ймовірність. Якщо після калібрування Brier погіршився — рекомендовано Platt scaling або робота в просторі raw proba.

### 8.6. Стійкість порога

Перетин bootstrap CI та near-optimal діапазону дає **безпечний діапазон порогів**, у якому висновок не змінюється. Це означає, що рішення не є крихким.

### 8.7. Зона ручного перегляду

Об'єкти в зоні `[t_low, t_high)` ескалуються до оператора. **Ми не приписуємо оператору точності** — це окремий сценарій з параметрами `p_op` і `c_op`. У базовій версії manual-об'єкти виключені з метрик (auto-only).

### 8.8. Підтвердження на test

Розбіжності TEST vs OOF у межах очікуваних. **Політику можна рекомендувати до розгортання з моніторингом.**

### 8.9. Що моніторити після розгортання

1. Розподіл каліброваних балів — data drift.
2. Частка manual_review (`≤ 15%`).
3. Частка auto_positive.
4. Precision / Recall на розмічених підмножинах.
5. Brier score.
6. Latency та throughput.
7. Частота активації top-k fallback.

### 8.10. Коли переглядати політику

- `manual_review > 15%` стабільно > 1 тижня.
- `Precision(auto+) < 0.60` або `Recall(auto+) < 0.80`.
- Brier зростає на > 20% від baseline.
- KS-тест розподілу балів p < 0.05 (data drift).
- Зміна `c_FP`, `c_FN` або `c_op` від замовника.
- Поява нових типів рельєфу, не представлених у `D_train`.

### 8.11. Напрями покращення

- Збільшити `D_train` для вужчого bootstrap CI.
- Використати 10-fold CV для стабілізації OOF-оцінки.
- Замінити `LogisticRegression` на ансамбль (RandomForest, GradientBoosting) з повторним аналізом сітки порогів.
- Додати окремий сценарій оператора з відомими `p_op`, `c_op`.
- Розширити аналіз чутливості на більшу кількість split.
